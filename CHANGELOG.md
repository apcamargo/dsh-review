# Changelog

## 0.2.1

- Fleet worker stops are now self-explanatory at the per-worker level. The 2026-10-18 phyle run made every gap below visible at once: a 70-file diff sharded the scan into 15 runs worth ~120 minutes of reviewer work through the 3-wide pool — exactly the 2400 s default call budget — so the budget cut three in-flight workers mid-run and left two queued, a reviewer hit its 20-minute timeout mid-probe, and a worker that had finished its analysis ended its turn with a prose summary instead of its structured result and was fully re-run (11 minutes, ~209k input tokens). Every stop had a cause; only the aggregate warning named it, and the per-worker roster reasons read as unexplained cancellations.
- Fixed the uninformative cancellation reasons on a spent call. When the call budget — not the user's cancel or the plugin unload — is what stopped the call, every affected roster entry and verifier unit now reads `failed (reviewer was cancelled when the call budget expired)` instead of a bare `was cancelled` (`budgetCancellation`, applied in both `executeScan` and `executeVerify` post-pool, idempotent, and only when `budgetSpent()` is true — a genuine turn/run cancellation keeps the bare wording). The scan's ⚠️ budget warning moved from the result tail (after the raw findings, where it buried under 22 findings in the live run) to directly under the `Scan finished:` headline, and now names the seconds (`The call budget (2400s) was spent…`) via the new optional `callBudgetMs` result field.
- Fixed the verify-side budget blindness: a budget-cut `deep_review_verify` returned its findings markdown with unverified findings and no indication that anything was re-callable — the structured `pendingRuns`/`budgetSpent` fields never reach the orchestrator (the render IS the output), so the only re-call advice anywhere was the scan's. A partial verification now renders `> ⚠️ N verifier run(s) did not finish (the <budget>s call budget was spent mid-verification). This verification is partial: call deep_review_verify again with the same groups and dropped findings to finish the pending runs.` after the coverage line.
- Fixed the worker containment install (the best-effort tool restriction + per-command guard) failing silently and self-defeatingly. The live run showed 18 workers with ZERO guard denials while reviewers ran `python3` probes and wrote scratch files into the reviewed tree (`cat > /abs/path` succeeded — the guard's own regex denies that command), because the single `try` block wrapped both installs: any `tools.restrict` throw (an allow name the child's tool view cannot restrict — web deployments compose tools per preset) also skipped the guard, and every failure path was a `logger.warn` on stdout, which the desktop app does not persist. The install is now `installWorkerContainment` (exported, unit-tested): the restriction and the guard install independently, the allow-list intersects the child view's `restrictableNames` before `restrict` so a name-plane mismatch degrades instead of throwing, and every degradation is a note returned on the `runAgent` result (`containment`), attached to roster entries and verifier units and surfaced as one deduped `containmentWarning` line in the scan output, the rendered scan text, and the verify markdown (`⚠️ N fleet worker(s) ran without full tool containment: …`) — the next mis-deployment names its cause in the tool result instead of nowhere.
- Fixed the worker output contract contradicting the structured-output seam. Both the reviewer and the verifier output blocks said `Reply with one JSON object and nothing else: {…}` — a text reply — while the harness captures a structured child's result ONLY from the `structured_output` tool call (the runtime's own system-prompt section says `only the tool call counts as your result`), and the runtime converts a worker that completes without a capture into a bare `stopReason: "error"` with no diagnostic. A worker following the prompt's reply framing ends its turn unstructured and its entire review is discarded to the retry. Both blocks now demand the tool call (`Finish by calling the structured_output tool exactly once … Only that tool call counts as your result`), and `runAgent`'s reason ladder words the runtime's stop reasons for a reader: `finished without reporting its structured result` (the bare-error/no-capture case), `ran out of output tokens (max-tokens)`, `was blocked (refusal)`, with provider diagnostics still appended.
- Tests: the containment suite mounts the REAL `@deepseek-ai/dsh-tools` `ToolRuntime` (the fleet suite's fake child accepted any `restrict` filter, masking the live failure mode) and asserts the allow-list restriction on a real scope, real guard denials through the `guardReason` waterfall, guard survival when `restrict` throws, the empty-restrictable and unresolved-child notes; new runtime cases cover the containment-warning surface end to end (degraded and clean), the budget-attribution roster state, the warning placement and seconds, the verify pending note (present on a spent call, absent on completion), and the stop-reason ladder; the prompt contract test pins the `structured_output` wording. No default changed: `deep.concurrency` stays 3 and `deep.callBudgetMs` stays 2400000 — the re-call contract already recovers a spent call, and the fixes make that legible instead of silent.

## 0.2.0

- Breaking: this release tracks harness **0.2.1‑rc.2** (the previous plugin release ran on 0.2.0‑rc.2). The seam migration below is the load-bearing change; everything else in this list is plugin-internal hardening that predates or accompanies it.

- The seam migration is now verified against the **real** harness packages, not only the suite's fakes: the full test suite runs with the workspace dependencies resolved at the published 0.2.1‑rc.2 packages (regenerating `package-lock.json`, which had been left at 0.2.0‑rc.2 while the manifest demanded the new ranges — `npm ci` was broken and `npm install` died in an `ERESOLVE` conflict until the stale lock was discarded; the stale tree also meant the suite had silently been passing against the old harness). A new `test/seam-contract.js` canary mounts the real `SubagentRuntime` on real cordis, applies the real `dsh-subagent-spawn-in-process` provider, and asserts the exact contract `runAgent` depends on — the `startActivation`/`getProvider` seam methods, the spawn provider's capability set (`agentOptions`, `agentPreset`, `outputSchema`, `depthLimit`) with `inheritsParentContext: false`, and the error ladder over the plugin's exact spec shape (unknown provider → `NO_PROVIDER`; a missing requested capability → `UNSUPPORTED_CAPABILITY` naming it before manager resolution; a fully-capable provider reached past `assertCapabilities` → `CONTINUATION_UNAVAILABLE`). The fake provider in the fleet suite mirrors the real shape, which is exactly how the 0.2.1 seam break shipped unnoticed; the canary now fails the suite on the next seam rename before a reviewer ever starts blank. The client-boot failure mode keeps its regression guard in `test/client-ui.js` (the `inject: ["slots"]` declaration assertion), so the standalone `repro-boot-failure.mjs` script is dropped.
- Version-range housekeeping: the cordis peer and dev ranges move to `~4.0.5` and schemastery to `~3.18.5` (the versions the harness bundle ships; the old `~4.0.4`/`~3.18.4` already admitted them — the bump documents the host), `@deepseek-ai/dsh-subagent-spawn-in-process` joins the dev dependencies for the canary, and the README gains the harness-compatibility rule: a linked checkout shadows the host bundle for the plugin's direct harness imports, so after every harness update the workspace's dev dependencies must be reinstalled at the running harness's version, and all `@deepseek-ai/dsh-*` ranges must move in lockstep (the harness packages cross-pin their inter-package peers exactly; a partially-bumped set fails resolution). The deep-concurrency documentation now notes the harness activation capacity (`maxActiveSubagents`, default 8) that bounds live fleet children per activation tree.
- Config: the deep scan and the deep verify phase now share ONE pool size. The verify phase used to run two parallel pools — `deep.verifierConcurrency` (3) for the static lanes plus `deep.executingConcurrency` (2) for the reproducers — so verification held up to 5 simultaneous agents while the scan held `deep.concurrency` (3). Both steps now run inside a single shared pool bounded by `deep.concurrency`, so a deep review never holds more than that many simultaneous agents in either phase; the reproducer bound survives as a scheduling sub-cap inside the shared pool (at most 2 reproducer lanes concurrent — they run tests in the shared working tree, and more than two concurrent test runs collide with each other), not as a second pool. `deep.verifierConcurrency` and `deep.executingConcurrency` are removed; `deep.concurrency` is the one knob (the harness activation capacity note now reads "raising `deep.concurrency` past ~7"). The pool scheduler is rewritten as `mapPoolTotal` (one in-flight budget, per-group sub-caps, forward-scanning dispatch so a sub-capped group cannot block an eligible later item, results in input order, callback throws still land as dropped `{ok:false}` values); the scan's degenerate single-group use of the old `mapPoolGrouped` moves onto the same helper and the grouped variant is gone. The verify-budget test's scripted pool arithmetic follows the new shape (the first call starts 3 children, not 4).
- Fixed `--deep` on the current harness build (subagent seam 0.2.1-rc.2): every reviewer failed its capability preflight with `the "spawn" provider does not support personas, so a fleet worker could not be composed`, the scan reached 0/7 quorum, and no worker ever started. The 0.2.1 release removed the per-provider `persona`/`toolFilter` capabilities and the `persona`/`toolFilter` start-request fields (persona and tool composition moved to agent presets) and replaced the one-shot `ctx.subagents.start(name, request)` seam with `startActivation(spec)` returning `{ childId, result, dispose }` — the plugin's preflight rejected the provider before it ever reached the (now-missing) call, and the suite never caught it because the fake provider still advertised the removed capabilities. The fleet now composes its workers on the new seam: the static lane persona is prefixed to the worker's prompt (it was always a static string, so the no-dynamic-text invariant holds; the verifier prompt no longer repeats its persona head, which the prefix replaces), the structured-output capability check and the inherits-parent-context refusal stay, and the tool allow-list is enforced on the child's own scope after publication — `tools.restrict({ allow })` for the declarative filter plus the unchanged per-command guard, both best-effort warnings, the child resolved through the agents registry since the activation receipt publishes no `localAgent`. The worker's timeout and the call budget now cancel through disposal (the manager does not watch the published signal; an abort listener disposes the activation), and callers get `delivery: "caller"` so no settlement message is injected into the orchestrator's inbox. No provider in a 0.2.1-rc.2 deployment advertises personas or tool filters, so switching `deep.reviewerProvider` could not have recovered; the documented provider requirement drops personas and tool filters accordingly. Peer and dev ranges move to `^0.2.1-rc.2` (the pre-release rule kept npm on 0.2.0-rc.2 even though the installed harness ships 0.2.1-rc.2); run `npm install` to refresh `node_modules`.

- Added `@` file-reference support to the folder snapshot mode. The composer's file picker inserts `@path` text into the command line (`@"path with spaces"` for whitespace, the open-quote `@"dir/` for directories), and the parser previously took those tokens verbatim: `/review folder @src` resolved a literal `@src/` directory that does not exist — a regular review sent the reviewer hunting a nonexistent path, and a `--deep` review's deterministic roster listing ran `git ls-files -- '@src/'`, matched nothing, and burned the fleet on an empty scope named only by the coverage note (`no requested path exists under the worktree: @src/`). Each folder path now strips one leading `@` marker after tokenization (`@src/` → `src/`, `@"My Docs"` → `My Docs`), and input whose every token carries the marker promotes to the folder mode without the keyword — `/review @src --deep` and `/review @lib/git.js` (the mode accepts single files) both start a snapshot review, with every flag composing as before. Mixed text (`@src error handling`) keeps the custom-focus reading, and a lone `@` is not a path. Folder paths are now taken from the tokens directly instead of re-splitting the joined remainder, which also fixes quoted paths containing whitespace (`folder @"My Docs"` previously parsed as the two paths `My` and `Docs`). The user-facing target label changes from `folders:` to `paths:` (the mode always accepted files), with the pinned prompt-snapshot hint updated. Composer-staged file attachments (paperclip / drag-and-drop / paste) are accepted on the same target too: `/review` now declares `input.attachments`, and each admitted file block resolves to its stored copy's full host path through the attachments service (`fileHostPath`) — a receipt carries only the attachment id, display name, and byte size, because an upload transmits bytes and never the original location, so the stored copy's path IS the attachment's full path. Attachments merge with the folder mode's paths (deduped by absolute resolution) and, when no mode is named, become the snapshot target themselves — a bare `/review` with attached files reviews those files; a git-diff mode or a free-form focus refuses the combination as a conflict, and image blocks are refused (a review target is a filesystem path). `/end-review` still refuses attachments. The plugin reads the optional store lazily (`ctx.get("attachments")`), so a deployment without an attachment store keeps loading the plugin, and only an attachment-carrying submission answers with the missing-store error.
- Fixed silent `/review` failures in the UI. A command that settled as an error was invisible: the harness composer deliberately never echoes an admitted command's outcome ("the outcome renders as a persistent flow node — the composer never echoes it"), and that flow node is unmounted in a session that has never started a model turn (`session.blank` clears only on `turn/start`; the conversation view returns `null` while `blank && phase === "blank"`). Running `/review --deep` as the first action in a fresh session therefore showed nothing at all — observed live on 2026-10-15, where two failing runs in a git-less workspace left only `command/done` entries in the harness logs and a permanently blank session. The package now ships a web client half (`dsh.client: { "platform": "web" }`, `./client` → `lib/client.js`, the `__ModuleLoader__` bundle format the UI's client-module system loads from any host loader entry) that restores visibility without patching the harness: (a) a `command/executed` listener raises settled `/review` and `/end-review` errors on the composer's notice channel — the input-bar notice renders in every shell phase including the blank hero — with a missing-sessions/conversation guard that degrades to silence; and (b) the `conversation.chat.commandview` keyed slot (`key: "review"`) replaces the generic command card with one whose error state is a loud, always-expanded, full-text failure card (command line echoed, run guidance beneath), while success and running outcomes stay quiet rows.
- The not-a-git-repository command error now names the directory it checked and the detection rule — `Checked <cwd>; a repository is detected by walking up from the session's working directory, so a repository in a subfolder is not seen` — and points at `/review <focus text>` alongside `/review folder <paths>`. Previously a repository below the workspace root (e.g. a project cloned as a subfolder of the session workspace) read as "not a git repository" with no hint where git looked.

- Fixed the mixed zero-succeeded simplification disclosure: when no simplification reviewer succeeded and only some failed (a shard failed while a sibling shard was still pending above quorum), the section named the pending reviewer among "the simplification reviewers failed (R4, R8)" although it never ran. `simplificationAuditState` now separates the still-pending ids (`pendingIds`, present only in the mixed case) and the disclosure names each reviewer by its real state (`the simplification reviewer failed (R4) and R8 was still pending when verification ran`), leaving every previously accurate line byte-identical; the `partial` disclosure also gained the "Re-run the review" pointer its contract promised (the only non-pinned line without one).

- Consistency evaluation now separates stated from inferred conventions in every surface that judges them. The rubric (regular mode), the consistency lens (deep scan) and the consistency lane persona (deep verify) define a codebase convention as either stated — a conventions file, a documented standard, a comment declaring intent — or inferred from recurrent patterns, with a stated convention outranking a contradicting recurrence. The lane's verdict bar follows: one cited precedent settles a stated convention; an inferred one requires multiple independent occurrences of the same pattern (single or conflicting occurrences are `unclear`), citing every location that establishes it. The report note renders those citations (up to three, then a count) — `departs from a codebase convention (precedents: \`a:1\`, \`b:2\` +1 more)` — replacing "the codebase pattern", whose definite singular overclaimed what one cited file:line proves (the citation gate verifies a quote at a location, never that the location represents a pattern). All 36 regular-prompt snapshots were regenerated for the rubric addition.

- Added always-on simplification evaluation to every review (regular and `--deep`), reported in a required non-blocking **`## Simplification Opportunities (Non-Blocking)`** section that never changes the verdict and never enters the fix queue (`/end-review fix` treats it as informational — a simplification is applied, if at all, in ordinary post-review work). The review reports opportunities; nothing edits code. Regular reviews evaluate the changed code against four shared principles (preserve functionality, apply project standards, enhance clarity, maintain balance — one constant shared with the deep lens, so the two surfaces cannot drift) with their own grounding bar; snapshot (folder/custom) reviews scope to the reviewed files. All 36 regular-prompt snapshots were regenerated for the rubric tail.
- Deep reviews run a `simplification` lens (a fourth file-local lens, sharded like the defect-local lenses) whose findings carry a plugin-derived kind (`simplification` vs `defect`, from the reviewer's lens — worker text and repository content can never set it) and are visible in the scan output via a fixed-position `[simplification]` tag. Consolidation enforces the kinds structurally: mixed-kind groups are rejected with a correctable error naming the ids, overlap hints cluster within kind only, and at most a third of `deep.maxVerifications`, rounded up, may be simplification groups (10 at the default) — the rest of the cap stays reserved for defect findings, so a `--aggressive` cleanup flood can never crowd defect verification out.
- Deep verification gained a `simplifier` lane (static, citation-gated, mandatory like the reproducer and the skeptic, chunkSize 8) that audits every simplification group: does the proposal preserve behavior exactly (callers traced), and is the result genuinely simpler? `simpler` confirms it as a "single-lane audit: no behavior change found" (the label describes what the lane did — one cited stance is not a proof); `behavior-change`/`not-simpler` refute with the lane's notes; a failed simplifier run leaves the finding unverified. Simplification findings normalize with two guards: an empty behavior-preservation argument drops the finding, and a P0/P1 priority clamps to P2. The provenance lane filters both kinds (a citation-verified pre-existing/intentional cleanup is dismissed); defect findings carry no simplifier lane-verdict row and simplification findings carry no defect-lane rows.
- The verified report always renders the simplification section (a defect-only report gains exactly the two empty-section lines); the fidelity gate requires its header beside every reported finding, so a report that omits the section costs one steer. `deep.maxReviewers` default rises 12 → 15: the smallest cap that keeps three shards per file-local lens once the simplification lens joins them, so the defect lenses keep their pre-simplification review depth on large diffs (small diffs run 7 reviewers). Dismissed simplification one-liners are marked "(simplification)".
- Simplification-report fixes (adversarially re-verified): the section has no render cap — every confirmed item renders, because the fidelity gate requires the verbatim copy to contain every confirmed title, so the previous 10-item truncation (reachable only with `deep.maxVerifications` ≥ 31) manufactured a fidelity steer no faithful copy could satisfy, and its "lowest-stakes omitted" line asserted a priority ordering the positional slice did not have; the flood bound remains the consolidation kind cap (a third of `maxVerifications`, rounded up). A review whose `deep.lenses` pin excludes the simplification lens now reports `- (not evaluated — the simplification lens is not in deep.lenses; add it to enable this audit)` instead of "- (none)" — the pinned-set configuration (documented) previously rendered "the simplifier lane audited … (none)" over an audit that never ran, with no disclosure anywhere. The consolidation instructions and the `deep_review_verify` parameter descriptions now agree that a group is "one entry per unique defect or simplification", and the blind-projection contract line names the simplifier beside the fix-auditor.
- The simplification section's honesty is now runtime-truth, not config-truth: the empty-state line and the intro derive from the scan roster (`simplificationAuditState`), so "- (none)" renders only when the simplification reviewer actually ran, and a reviewer that failed or was still pending above the quorum — or a lens cut by `deep.maxReviewers` — is disclosed by id (`- (not evaluated — the simplification reviewer failed (R4); the audit did not run. Re-run the review to retry it)`, `- (partially evaluated — …)` when sharded coverage is incomplete, the disclosure line also rendering beneath items). Previously a failed reviewer above quorum rendered "- (none)" over an audit that never ran, disclosed only as a bare "6/7 reviewers succeeded" coverage count. The section's intro asserts "the simplifier lane audited" only when the audit provably ran with every item confirmed; the unaudited count line pluralizes its pronoun with the item count; and the two moderation branches share the lane-row rendering and the provenance-dismissal logic (`laneRow`/`provDismissReasons`), so the promised defect/simplification parity cannot drift. Known edge left open: `deep.minReviewerSuccess: 0` (schema-legal) still lets an all-failed fleet produce a "nothing survived" report — the whole-report degraded marker is a separate concern. The disclosure is now also sampled at the FIRST verify call and stored on the run (`run.verify.simplificationAudit`) instead of resampled at the completing call: a scan re-call that heals a pending or failed simplification reviewer after consolidation began can no longer flip the shipped section's disclosure to "- (none)" over findings the verification never saw — the healed finding stays unconsolidated (the input-hash guard rejects a different consolidation), and the disclosure keeps naming the reviewer that was lost when the consolidation was built, with the re-run advice still correct.
- Added `--timeout <seconds>` to `/review`: a per-run fleet timeout parameter. The flag (integer seconds, 1–2147483 — a missing value, a non-integer, or an out-of-bounds value answers the flag's error; duplicates: last wins; requires `--deep`) sets BOTH worker limits — reviewers and verifier lanes — for that review only, and raises the call-budget headroom to at least (1 + retries) × each limit so a timed-out worker's in-call retry actually fits. The merge happens at the fleet's begin (where the settings resolve once per run), not the command handler; a live review's settings are deep-frozen, so the flag never changes a run that already began, and `deep_review_scan` re-calls finish pending reviewers under the settings the review began with. The start message names the effective worker limit and budget; `/review status` shows the hint. `--extra "--timeout 900"` still stores the literal (both flag forms are guard values now). The default `deep.reviewerTimeoutMs` is 1200 s (previous caps kept killing long analyses mid-run — the consistency lens died at exactly 600,003 ms with zero failed requests, so the cap, not a failure, decided what the review saw); `verifierTimeoutMs` stays 600000, and a reviewer that burns its full limit stays bounded by `deep.callBudgetMs` and the retry loop's aborted check.
- Config: `deep.callBudgetMs` now scales when unset — at least (1 + retries) × the worker timeouts, max over both kinds, derived after the timer clamps and clamped to MAX_TIMER_MS. With the 1200 s default timeout equal to the old 1200 s default budget, a full-timeout worker's in-call retry was dead by construction and wave-2+ workers were budget-cut before their own timeout fired; the unset-budget floor fixes the default pair and the config-timeout-only hole (`deep.reviewerTimeoutMs: 1800000` alone now yields a 3600 s budget). An explicitly-configured budget stays a cap — silently raising a user's explicit cost cap would violate it, and the four budget-pinning runtime tests keep their small explicit budgets.

- Fixes (fleet reliability): each reviewer now gets one in-call retry — the same attempt loop the verifier units keep (`deep.verifierRetries`) — before its roster entry is declared failed, behind the new `deep.reviewerRetries` (default 1). In the last observed `--deep` usage two of six reviewers (correctness, propagation) died from one mid-stream provider failure each (`litellm.APIConnectionError` — the chunked response was severed, `Connection reset by peer`; both within 2.4s of each other while three workers streamed), and nothing re-spawned them: a worker whose single LLM attempt ends `finish: error` fails its entry, its lens stays uncovered for the whole review, and recovery needed a manual `deep_review_scan` re-call the orchestrator never made. The aborted check re-runs before each attempt, so a spent budget, a cancelled turn or an unloaded fleet breaks instead of re-spawning into an abort (a budget-killed worker is still not retried; the spent-call contract returns what is pending). A persistently-failing worker still ends failed after exactly one retry per call (regression-tested: a first-attempt failure is recovered by the in-call retry with no re-call, and a doomed worker runs exactly twice per scan call and still fails).

- Fixes (web deployment): the deep fleet's reviewer-tool visibility check now resolves `deep.reviewerTools` against the calling session's tool view — `ctx.tools.get(name, parent)`, the scoped lookup the tools service itself uses for a call (`this.get(name, agent)` in createExecution) — instead of a no-scope `ctx.tools.get(name)`, which reads the host composition's GLOBAL layer only. The web-app bundle moves every model-facing tool behind per-session presets on the agent plane (its patch disables the base's host `tool-bash`/`tool-fs`/`tool-fs-search` rows and lets each session mount a preset instead), so the global view reads "bash" as absent in a web deployment and every reviewer of a passing session failed with `the configured reviewer tool "bash" is not visible to this session` — a deterministic failure the scan's "Call deep_review_scan again to retry them" steer could never recover. A genuinely missing tool still fails loud with its name (regression-tested over a preset-scoped web-profile-shaped tool view).

- Fixes (evaluation round 2): -z path parsing no longer trims — filenames with leading/trailing whitespace are legal and tracked verbatim, so the working-tree snapshot now stats the exact path (both snapshots recording "deleted" under the trimmed key silently disabled the "files changed during review" guard for such a file) and the untracked roster entry resolves the exact filename, matching the verbatim numstat parse. `resolveDeepConfig` now re-checks the lane entry shapes — a non-object lane value (`reproducer: "off"`) and a non-boolean `enabled` would pass validation and be silently ENABLED at runtime, so a user disabling the mandatory lane got it run; both throw with the field path. `/review --extra "--deep"` — an explicitly-quoted literal — is no longer answered with "Missing value for --extra": control-vs-value is decided on the raw remainder after `--extra` (the instructions path's own convention; `--extra=--deep` already stored the literal, and the bare `--extra --deep` is still the control word the guard rejects).

- Deep review fixes (evaluation round): a scan above `deep.minReviewerSuccess` with failed reviewers now counts for verification — `deep_review_verify` and the stop gate share one quorum notion (`scanCounted`), so one persistently-failing reviewer above quorum (whose doomed worker each scan re-call re-runs) can no longer leave verification permanently unreachable and the review ends with zero verification; failed reviewers' scopes are uncovered, the coverage line reports the success count, and the verify gate names the fraction and the pending or failed reviewers. The folder walk now names every non-regular entry — a symlinked directory inside a reviewed folder, a FIFO — in the coverage note with per-path reasons instead of a silently complete walk. Dead stores on the run record (`run.scan.result`, `run.scan.rendered`, `run.verify.rendered`, `run.verify.tree`) are dropped; only `run.verify.classified` is consumed beyond the stored results.

- Review-finding fixes (independently adversarially re-verified): the citation gate now confines every cited path to the reviewed worktree before it stats or reads — evidence paths are LLM-authored (the verifier lanes' normalized results) and reach `node:fs` directly, so an absolute or `../`-escaping path, and a worktree-internal symlink whose realpath escapes, is refused without reading (≤10 MB host reads and an existence oracle over files outside the worktree; the contract is containment, not spelling: an absolute path that resolves inside the worktree is allowed). The working-tree snapshot now rides `git status --porcelain -z` beside `git ls-files -m -d -o` — the latter lists the worktree against the index only, so a mid-review `git add`/`git mv`/`git rm` was invisible and the before/after snapshots matched, silently off for the "files changed during review" guard (status also answers 0 on a repository with no commits, where `git diff HEAD` would fail; the parse skips the rename-source NUL record a staged rename emits, so the source is not hashed as a phantom "deleted"). `/review status` and `/end-review status` now render `Pipeline: gone` for a deep record whose in-memory fleet cleared on restart, instead of an active review with no pipeline line (the README says the status says so). A failed review-turn send after `begin` + durable write now rolls the deep run back (the converse of the durable-write rollback; the durable record still says active, so `/end-review done` recovers). `--extra` answers "Missing value" for every form the partition accepts directly after it (`--deep=true`, `--aggressive=false`, `--extra=...` were silently consumed as the value); `--aggressive=false` and any other `--aggressive=<value>` but the tolerated `=true` now answer the flag's error instead of silently enabling the mode (symmetric with `--deep`). A fleet worker whose provider ignores the composed signal and resolves `completed` across an abort now answers not-ok with the cancel or per-run timeout diagnostic (the configured limit stays hard; the worker re-runs). A `bash` command with more substitution spans than the worker guard inspects (the 8/12 caps) now denies the command outright instead of passing because its first spans were clean. A duplicated `deep.lenses` name throws instead of running the lens's reviewers twice; the returned deep settings are deep-frozen over a clone (freezing never side-effects the caller's config object); a drifted rubric split marker fails loud at load instead of silently truncating the rubric; and the folder walk's dot-dir convention (skip all but `.agents`) is documented in the walk and the README.

- Review-finding fixes (independently adversarially re-verified): the read-only worker guard now denies the ref/file write options of the whitelisted read `git` subcommands — `git branch -d/-D/-m/-M/-c/-C/-f/-t/-u/--delete/--move/--copy/--force/--track/--set-upstream-to/--unset-upstream/--edit-description` and `git show/log/diff/blame --output=<file>` (real-git verified writes; the same ref-write class the subcommand deny list covers for checkout/reset/stash/rebase) — and the no-space redirect to an absolute path (`git show HEAD >/abs/f`), closing the `>/` slip the space form never had. A scan with nothing to verify — zero findings, or every finding dropped — now completes with an explicit empty consolidation: the previously-advertised "skip deep_review_verify" escape was impossible and dead-ended the stop gate into a false incomplete marker. - Added `/review --deep`: fleet review mode. A scan stage runs one fresh reviewer per lens (correctness, failure paths, security, contracts, consistency, propagation; performance opt-in) in a bounded pool, sharding large diffs; the orchestrator consolidates and groups the raw findings; and a verification stage of independent adversarial lanes (reproducer, skeptic, consistency, provenance, impact, fix-auditor) judges each consolidated finding blind to the orchestrator's reasoning and to every other lane. A deterministic moderator combines the lane stances (refutation via the gating lanes needs two independent dimensions to agree; the provenance filter dismisses a citation-verified pre-existing or intentional finding regardless of gate status), a citation gate checks cited evidence against the real files, and only verified findings reach the report. `--aggressive` reports unproven findings as low-confidence suspicions; the final filter is unchanged without the flag.
